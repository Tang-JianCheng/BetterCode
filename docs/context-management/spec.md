# BetterCode 上下文管理 Spec

## 背景

BetterCode 已具备 Agent Loop、流式事件、六个内置工具、权限系统、结构化系统提示和 MCP 工具接入。Agent 可以在一次任务中持续调用模型和工具，但当前会把用户消息、模型回复和工具结果完整累积在内存历史中，并在每次模型请求时全部发送。

长任务中的主要 Token 消耗来自文件内容、命令输出、代码搜索结果和 MCP 工具结果。历史持续增长后，请求可能逼近或超过模型上下文窗口，导致模型请求失败，Agent 无法继续工作。简单截断历史又会丢失任务目标、用户约束、已完成工作和工具调用关系。

本章为 BetterCode 增加两层上下文管理：先对过大的工具结果做轻量落盘，再在整体请求接近上下文窗口时生成结构化摘要。系统优先保留用户原始消息和近期完整上下文，在近似 Token 估算存在误差的情况下提前留出安全余量。

## 目标

- 在每次正常模型请求前控制单轮工具结果和累计历史的上下文体积。
- 将过大的工具结果安全存放在项目目录内，对话中只保留可识别预览和可重新读取的路径。
- 在累计历史接近模型窗口时，用独立模型请求生成结构化摘要，替换较早的模型回复和工具交互。
- 保留全部可保留的用户原始消息，并完整保留近期约 10K Token、且不少于 5 条消息的上下文。
- 使用 API 返回的输入 Token 用量作为估算锚点，只对锚点后的历史变化做近似估算。
- 支持用户手动触发压缩，并在自动摘要连续失败时熔断，避免 Agent 陷入重试循环。
- 通过异步事件向界面报告压缩进度、结果和失败原因，不把上下文管理耦合到 TUI。

## 配置约定

每个 LLM 供应商配置支持声明模型上下文窗口大小。配置值表示一次请求可接受的最大输入与预留输出总 Token 数，必须为正整数。

为兼容现有配置，未声明时使用 128K Token 的默认窗口，并产生一次不含敏感信息的提示，建议用户为未知或自定义模型显式配置。显式配置始终优先，BetterCode 不根据模型名称维护易过期的内置窗口名单，也不请求外部模型元数据服务。

上下文管理默认使用以下阈值，后续技术设计可以提供同等语义的可配置入口：

- 单个工具结果落盘阈值：约 8K Token。
- 同一模型响应对应的工具结果合计上限：约 16K Token。
- 对话中的单个落盘预览上限：约 1K Token，兼顾开头和结尾内容。
- 重量压缩后的近期原文目标：约 10K Token，且至少 5 条消息。
- 自动重量压缩安全余量：13K Token。
- 手动压缩请求可用安全余量：3K Token。
- 自动摘要连续失败熔断阈值：3 次。

阈值比较使用同一套近似 Token 估算，不要求引入精确 tokenizer。

## 功能需求

### F1：请求前两层管理流程

每次正常模型请求前，BetterCode 必须按固定顺序处理当前请求上下文：

1. 先运行轻量预防，检查尚未落盘的工具结果体积。
2. 基于处理后的完整请求估算 Token，包括稳定系统提示、动态指令、工具定义和对话历史。
3. 达到重量压缩触发线时生成并应用历史摘要。
4. 使用处理后的上下文发起正常模型请求。

这一流程适用于普通对话、Act Mode、Plan Mode，以及同一次 Agent Loop 中工具执行完成后的下一轮模型请求。不得只在用户发起新消息时运行，也不得让 MCP 工具绕过处理。

轻量预防和重量压缩都不得改变稳定系统提示和工具定义，避免破坏既有缓存策略。

### F2：单个工具结果落盘

单个工具结果超过默认约 8K Token 阈值时，BetterCode 将 Agent 实际收到的完整结果存放到当前项目的会话级上下文目录。现有工具执行层已经截断的内容不在本章恢复范围内，落盘内容以 Agent 收到的结果为准。

原工具消息在对话历史中的位置、角色、工具调用标识、工具名称和成功或失败状态保持不变，只将正文替换为有界占位内容。占位内容至少包含：

- 结果已落盘的明确说明。
- 工具名称和原工具调用标识。
- 项目内可重新读取的相对路径。
- 原结果的近似 Token 数或字节数。
- 能帮助模型判断是否需要重读的头尾预览。
- 用于识别文件完整性的稳定摘要值。

轻量处理必须幂等。已经替换为落盘占位的结果不得重复写入新文件，也不得在每轮请求前继续缩短预览。

### F3：同轮工具结果总量控制

同一次模型响应可能返回多个工具调用。完成单个结果检查后，如果这批工具结果保留在对话中的正文合计仍超过默认约 16K Token，BetterCode 按原始体积从大到小选择尚未落盘的结果依次落盘，直到合计不超过上限或已无可落盘结果。

体积相同时使用工具调用原始顺序作为稳定排序依据。处理不得改变工具调用与工具结果的顺序和一一对应关系，也不得拆散 Provider 要求成组出现的工具调用消息与结果消息。

被选择结果的替换格式与单结果落盘一致。合计值按替换后的实际占位内容重新计算，不能只按原结果体积推断。

### F4：落盘路径与生命周期

上下文文件只能写入当前项目根目录下的 `.bettercode/context/` 会话级目录。路径必须经过与现有项目沙箱一致的真实路径和符号链接检查，不得通过预先创建的符号链接、路径穿越或竞态写到项目外。

不同 BetterCode 进程和会话使用互不冲突的目录及文件名。文件采用限制当前用户访问的权限，并使用原子写入，避免模型收到尚未写完整的路径。

`/clear` 清空会话历史时同步清理当前会话的上下文文件。BetterCode 正常退出时清理仅属于当前进程且不再被历史引用的临时文件。异常退出留下的过期会话目录可在后续启动时按保守规则清理，但不得删除当前活动会话或用户自行创建的其他 `.bettercode` 内容。

上下文临时目录默认不应进入 Git 版本控制。落盘失败时必须保留原工具结果，不得先替换历史再报告成功。

### F5：近似 Token 估算

BetterCode 不引入精确 tokenizer，而是维护请求级近似估算：

- 最近一次成功完成的正常模型请求若返回输入 Token 用量，则该用量成为对应请求快照的估算锚点。
- 锚点之后新增、删除或替换的内容，使用确定性的字符数近似规则计算增量，并叠加到锚点。
- 如果没有可用 API usage、Provider 不返回 usage、历史经过重量摘要而无法继续复用锚点，或请求结构与锚点不兼容，则对当前完整请求使用同一近似规则重新估算。
- 摘要专用请求的 usage 不得覆盖正常对话请求的锚点。
- 估算不得把缓存命中 Token 当成从上下文中消失；缓存影响费用和延迟，不改变窗口占用判断。

字符估算规则应对英文、中文、代码和 JSON 采用保守权重，优先略高估而不是明显低估。所有阈值判断、进度信息和测试使用同一估算口径。

### F6：自动重量压缩触发

轻量预防完成后，BetterCode 估算即将发送的完整正常请求。当估算值达到或超过“模型上下文窗口减 13K Token”时，在发送正常请求前触发重量压缩。

自动触发线中的 13K 余量用于容纳估算误差、摘要指令、模型摘要输出和后续正常响应。若配置的上下文窗口小到无法同时容纳最低保留区、摘要请求和安全余量，系统应给出配置或容量不足错误，不得进入反复摘要。

重量压缩只在存在可压缩的较早模型回复或工具交互时执行。若主要体积来自稳定系统提示、工具定义、全部用户原文或必须保留的近期消息，系统应明确说明没有足够的可压缩内容，并停止当前模型请求。

### F7：近期原文保留边界

重量压缩从历史尾部向前选择近期原文，直到保留内容同时满足以下条件：

- 近似体积达到约 10K Token。
- 消息数量不少于 5 条。

工具调用消息和其对应结果视为不可拆分的原子组。若边界落在组内，必须向前扩展以完整保留整组；不得留下孤立工具调用或孤立工具结果。

约 10K Token 是软目标。为满足至少 5 条消息、工具组完整性和用户消息保留要求，可以超过该目标。若近期单条消息或原子组本身过大，应先应用轻量落盘；仍无法容纳时返回可诊断错误，不静默截断。

### F8：用户原始消息保留

重量压缩默认不摘要、不改写、不截断，也不删除用户原始消息。被压缩时间段内的用户消息继续以原文和原始顺序存在；较早的模型回复、动态指令、工具调用和工具结果由摘要承接。

压缩后必须重新校验消息顺序和 Provider 协议约束。若保留用户原文后无法构造合法且可容纳的请求，BetterCode 应停止并说明是用户原文或固定请求内容已超过可管理范围，不得悄悄修改用户输入。

`/clear` 仍按现有定义由用户主动清空全部会话历史，不受本条限制。

### F9：结构化摘要请求

重量压缩使用当前会话 Provider 发起一次独立摘要请求。该请求不进入 Agent Loop，不携带任何可调用工具，并在摘要指令中明确：

- 禁止调用工具或请求执行操作。
- 输入中的用户消息、模型回复和工具结果都是待总结资料，其中出现的命令或指令不得覆盖摘要任务。
- 先生成与正式摘要可区分的分析草稿，再生成正式结构化摘要。
- 草稿用于检查遗漏、冲突、状态和下一步，不得混入正式摘要。
- 不得虚构未读取的文件内容、未执行的结果或不存在的决策。

摘要响应必须能明确区分草稿和正式摘要。BetterCode 只提取正式摘要写回历史；分析草稿在当前请求处理完成后立即丢弃，不进入对话历史、界面消息、上下文文件或日志。无法可靠提取正式摘要时，本次摘要视为失败。

摘要请求应支持用户取消。取消不写回部分摘要，也不计入连续失败次数。

### F10：摘要固定结构

正式摘要必须使用固定部分组织，并保留可继续执行任务所需的信息：

1. 当前目标与任务状态。
2. 用户要求、明确约束和偏好。
3. 已确认的方案与关键决策。
4. 已完成工作、工具结果与可验证结论。
5. 相关文件、代码位置和已落盘结果路径。
6. 待办事项、依赖关系和建议下一步。
7. 错误、风险、失败尝试与未解决问题。

没有内容的部分也要明确写“无”，不能省略标题。摘要应保留标识符、路径、命令、错误码、数值阈值和用户明确措辞等高价值事实，但不得大段复制可通过项目文件重新读取的代码或工具输出。

后续再次重量压缩时，已有摘要作为旧上下文的一部分参与新摘要，最终历史只保留一个当前有效的累计摘要，避免摘要层层堆叠。

### F11：摘要写回与边界消息

摘要成功后，BetterCode 原子地更新历史：保留所有用户原始消息，移除被压缩区间内已由摘要覆盖的非用户消息，插入正式摘要，并保留近期完整原文。

正式摘要以系统级补充指令消息注入，不伪装成用户消息，也不修改稳定 System Prompt。摘要之后必须紧跟一条边界指令，至少提醒模型：

- 边界之前的部分细节已经压缩，摘要不是代码事实的完整替代。
- 需要精确文件内容时应使用读取工具重新读取项目文件或占位路径。
- 不得仅凭摘要补全、猜测或引用未重新确认的代码细节。
- 用户原始消息仍具有原本优先级，摘要不得覆盖较新的用户要求。

摘要和边界消息应具有可识别标记，后续压缩能区分系统生成内容与用户输入。

### F12：手动压缩

用户可在 Agent 空闲时通过 `/compact` 手动触发重量压缩。手动压缩即使尚未达到自动触发线也会尝试执行，只要存在可压缩的较早历史。

手动摘要请求在发送前使用“模型上下文窗口减 3K Token”作为可用上限。3K 余量只用于判断摘要请求能否安全发送，不改变压缩后的近期原文目标、用户原文保留规则或后续正常请求的 13K 自动安全余量。

手动压缩不得添加一条新的用户对话消息，也不得被模型当成业务任务回答。完成后界面显示压缩前后估算、被落盘结果数量、摘要覆盖消息数量和当前熔断状态。没有可压缩内容时返回明确提示，并保持历史不变。

Agent 运行、等待权限确认或已有摘要请求进行中时，不允许并发启动手动压缩。

### F13：失败计数与熔断

摘要请求因流错误、Provider 错误、响应格式无效、正式摘要为空或历史写回校验失败而失败时，保留压缩前历史，并将会话级连续失败计数加一。一次成功摘要将计数清零；`/clear` 也会重置计数和熔断状态。

连续失败达到 3 次后，自动重量压缩进入熔断状态。本会话后续请求不再自动发起摘要请求，而是直接返回清晰的上下文管理错误，提示用户检查 Provider、调整上下文窗口、执行 `/compact` 重试或清空会话。

熔断仅阻止自动重试。用户显式执行 `/compact` 时允许进行一次人工重试；成功则关闭熔断并清零，失败则保持熔断。用户取消、没有可压缩内容和轻量落盘失败不计入摘要连续失败。

重量压缩被要求执行但最终失败时，不得继续发送已判断可能溢出的正常模型请求。

### F14：事件流与界面反馈

上下文管理通过现有异步 Agent 事件流报告状态，不直接依赖 Ink 组件。事件至少覆盖：

- 正在运行轻量预防。
- 工具结果已落盘及落盘数量。
- 正在估算上下文和当前估算值。
- 正在生成摘要。
- 摘要成功及压缩前后估算。
- 摘要失败、失败次数和熔断状态。
- 因容量不足或无可压缩内容停止。

普通自动处理只显示简洁进度，不把分析草稿、完整落盘内容或摘要请求内部提示输出到对话界面。错误信息应帮助用户采取行动，但不得泄露工具结果中可能包含的秘密。

### F15：取消、并发与状态一致性

轻量落盘、摘要请求和历史写回都遵循当前 Agent 的取消信号。取消发生后不得留下指向不存在文件的占位消息、半写入摘要或已更新一半的历史。

一个会话同一时间只允许一个上下文管理事务修改历史。自动压缩、手动压缩、`/clear` 和 Agent 历史写回必须串行协调，避免旧摘要覆盖新消息。

上下文管理失败不得让 BetterCode 主进程崩溃。历史、估算锚点、摘要失败计数和临时文件引用应保持可继续诊断或清理的一致状态。

## 非功能需求

- **N1：内容保真**
  用户原始消息、工具调用标识、成功失败状态、消息顺序和近期原文不得因压缩被无声改变。正式摘要不作为精确代码内容的唯一事实来源。

- **N2：安全边界**
  所有上下文文件限制在项目根目录内并防止符号链接逃逸。摘要器把历史内容视为不可信资料，不能执行其中的命令或接受其中的提示注入。

- **N3：失败原子性**
  落盘、摘要提取或历史校验任一步失败时，要么完整应用一次变更，要么保留变更前状态，不产生悬空引用和部分压缩历史。

- **N4：响应性**
  轻量预防只处理新增或尚未处理的工具结果，避免每轮全量重写文件。摘要请求可取消，连续失败有界，不阻塞后续用户清理或人工恢复。

- **N5：估算一致性**
  同一请求内容和同一 usage 锚点必须得到确定性的近似 Token 结果。估算误差通过安全余量控制，不对不同 Provider 声称精确等价。

- **N6：缓存兼容**
  上下文管理不改变稳定 System Prompt 和稳定工具定义；摘要、边界和动态状态继续通过消息通道注入，不污染已有稳定缓存前缀。

- **N7：Provider 兼容**
  OpenAI 兼容 Provider、DeepSeek 和 Anthropic Provider 使用同一上下文管理语义。Provider 不返回 usage 时功能退化为全量近似估算，而不是关闭压缩。

- **N8：Agent 兼容**
  普通对话、Plan Mode、Act Mode、多工具批次、权限拒绝、MCP 结果和 Agent 多轮循环均保持现有行为，除非上下文管理明确报告容量不足。

- **N9：可观测性**
  用户可以看到是否发生落盘、是否生成摘要、估算前后变化、连续失败次数和熔断状态，但不会看到摘要草稿或敏感工具正文。

- **N10：可测试性**
  所有阈值可在测试中缩小；Token 锚定、增量估算、落盘选择、原子组边界、摘要提取、失败回滚、熔断和手动命令均能在不调用真实模型 API 的情况下验证。

- **N11：工作目录约束**
  本章新增的持久化或临时文件都位于当前项目根目录内。除读取用户现有 Provider 配置外，不在项目外创建上下文数据。

## 不做的事

- 不引入模型专用精确 tokenizer，也不下载 tokenizer 词表。
- 不维护模型名称到上下文窗口的在线或内置映射表。
- 不实现基于机器学习、向量检索或重要性打分的摘要策略优化。
- 不把用户原始消息自动摘要、改写、去重或纠错。
- 不自动读取已落盘工具结果；是否重读由模型根据占位预览和当前任务决定。
- 不恢复工具执行层已经按输出上限截断、且从未交给 Agent 的内容。
- 不持久化完整会话，不支持退出后恢复摘要历史。
- 不实现跨会话共享摘要、长期记忆或项目知识库。
- 不对摘要内容做事实正确性的自动代码级验证，只校验结构、完整性和消息协议合法性。
- 不修改权限系统规则；模型重新读取落盘文件时仍按现有工具权限和 Plan Mode 规则执行。
- 不压缩稳定 System Prompt、工具 Schema 或当前轮必须发送的动态环境指令。
- 不在摘要失败后自动切换 Provider、缩短用户消息或无限重试。
- 不实现图形化上下文浏览器、摘要编辑器或落盘文件管理界面。

## 验收标准

- **AC1：请求前顺序**
  在同一 Agent 任务中产生大工具结果后，下一轮模型请求前依次观察到轻量处理、Token 估算和必要的重量压缩；发给 Provider 的稳定系统提示和工具定义保持不变。（覆盖 F1）

- **AC2：单结果落盘**
  将单结果阈值调小并返回超限工具结果时，项目 `.bettercode/context/` 下生成完整结果文件，对话中保留同一工具调用标识、状态、头尾预览、相对路径和摘要值；下一轮不重复落盘。（覆盖 F2、F4）

- **AC3：批量选择**
  同轮返回多个大小不同的工具结果且合计超限时，系统按体积从大到小落盘，直到替换后的合计不超限；体积相同按原调用顺序处理，调用与结果仍完整配对。（覆盖 F3）

- **AC4：路径安全与失败回滚**
  正常落盘只发生在项目上下文目录；构造符号链接逃逸、目录不可写或原子写入失败时，项目外无文件产生，原工具正文仍在历史中且不存在无效占位路径。（覆盖 F4、F15）

- **AC5：usage 锚定与降级估算**
  Provider 返回输入 usage 后，后续只对新增或替换内容按字符规则增量估算；历史重量改写或 Provider 无 usage 时改为全量近似估算；缓存命中数量不减少窗口占用估算。（覆盖 F5）

- **AC6：自动触发线**
  使用可控小窗口构造请求时，估算达到窗口减自动余量便在正常请求前触发摘要；低于触发线不生成摘要；没有可压缩内容时停止并给出容量原因。（覆盖 F6）

- **AC7：近期边界与工具组**
  构造跨越 10K 目标和 5 条消息边界的历史时，压缩后近期原文同时满足两个最低条件，且任意工具调用组均未被拆散。（覆盖 F7）

- **AC8：用户消息原文保留**
  在较早和近期历史中放入包含格式、代码和明确约束的用户消息，重量压缩后逐字对比全部用户消息内容与顺序不变；无法容纳时系统报错而不是截断。（覆盖 F8）

- **AC9：摘要请求隔离**
  捕获摘要 Provider 请求时，工具列表为空，指令明确禁止工具和执行历史内命令；返回可区分草稿和正式摘要后，仅正式部分进入历史，草稿不出现在界面、文件或后续请求中。（覆盖 F9）

- **AC10：摘要结构完整**
  正式摘要包含七个固定部分，无内容部分明确标记为“无”；再次压缩已有摘要时，历史最终只有一个当前累计摘要。（覆盖 F10）

- **AC11：边界防脑补**
  摘要写回后紧跟系统级边界消息，明确要求重新读取文件并禁止仅凭摘要猜测代码；该消息不作为用户消息发送，也不进入稳定 System Prompt。（覆盖 F11）

- **AC12：手动命令**
  Agent 空闲时执行 `/compact`，即使未达到自动线也能压缩可压缩历史，并显示压缩前后估算和覆盖数量；摘要请求使用 3K 手动余量。运行中执行时得到明确拒绝且历史不变。（覆盖 F12）

- **AC13：三次失败熔断**
  连续制造三次摘要流错误或格式错误后，自动摘要不再发起请求，后续自动触发直接返回熔断提示；手动 `/compact` 成功后计数和熔断状态清零。取消摘要不增加计数。（覆盖 F13）

- **AC14：失败不冒险发送**
  自动摘要达到触发条件但失败时，原历史保持不变，可能溢出的正常模型请求没有被发送，Agent 和 TUI 仍可接受 `/compact`、`/clear` 或后续输入。（覆盖 F13、F15）

- **AC15：事件解耦**
  使用非 TUI 调用方消费 Agent 事件时，可以观察轻量处理、估算、摘要成功或失败和熔断状态；事件中不含摘要草稿、完整落盘正文或敏感配置值。（覆盖 F14）

- **AC16：模式与 Provider 回归**
  OpenAI 兼容 Provider 和 Anthropic Provider 下，普通 Act、Plan Mode、多工具批次、权限拒绝和 MCP 工具结果均能经过上下文管理继续运行；Provider 无 usage 时仍可自动压缩。（覆盖 F1、F5、F15）

- **AC17：清理行为**
  `/clear` 后历史、估算锚点、失败计数、熔断状态和当前会话上下文文件均被清理；不会删除其他会话或用户在 `.bettercode` 下的无关内容。（覆盖 F4、F13）
