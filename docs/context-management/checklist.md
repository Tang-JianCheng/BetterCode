# BetterCode 上下文管理 Checklist

> 每一项都通过运行测试、执行命令或观察事件验证。自动化测试只使用临时项目和受控 Fake Provider，不访问真实模型 API、公网 MCP Server 或项目根目录外的上下文文件。实现完成前所有项目保持未勾选。

## Provider 配置与请求边界

- [ ] **C1：显式上下文窗口正确生效** 配置 `context_window: 128000` 后，OpenAI 与 Anthropic Provider 均暴露 128000，且标记为非默认值。（验证：运行 `pnpm exec tsx --test src/config/loader.test.ts src/provider/openai.test.ts src/provider/anthropic.test.ts` 的显式窗口场景；覆盖 AC16）
- [ ] **C2：缺省窗口兼容并提示** 旧配置不含 `context_window` 时仍能加载，Provider 使用 128K，TUI 只显示一次显式配置提示且不包含密钥。（验证：运行 Provider 与 App 默认窗口测试；覆盖 AC16）
- [ ] **C3：非法窗口在配置阶段拒绝** 零、负数、小数和字符串窗口均产生带 Provider 名称和字段名的中文错误，不能进入 Provider 创建阶段。（验证：运行 `src/config/loader.test.ts` 非法值矩阵）
- [ ] **C4：摘要输出上限正确映射** 摘要请求在 OpenAI 和 Anthropic 请求体中均限制为 2048 Token，普通 OpenAI 请求不新增上限，普通 Anthropic 仍为 4096。（验证：捕获两种 Provider 请求体并比较字段；覆盖 AC9、AC16）
- [ ] **C5：内部消息元数据不进入 API** `instructionKind` 和 `contextReference` 只存在于 BetterCode 内部消息，OpenAI 与 Anthropic 请求体不包含这些字段。（验证：运行两种 Provider 内部元数据映射测试；覆盖 AC2、AC11）
- [ ] **C6：稳定缓存前缀不被改写** 轻量和重量压缩前后，正常请求的稳定 System Prompt 与工具定义内容、顺序和 Anthropic cache_control 位置保持一致。（验证：比较压缩前后捕获请求；覆盖 AC1、AC16）

## Token 估算

- [ ] **C7：字符估算确定且偏保守** 相同英文、中文、代码和 JSON 输入多次得到相同整数，中文不按 ASCII 4:1 比例低估。（验证：运行 `pnpm exec tsx --test src/context/token-estimator.test.ts` 的字符估算场景；覆盖 AC5）
- [ ] **C8：完整请求字段全部计入** System Prompt、动态 instruction、用户/助手/工具消息、工具名称、描述和 Schema 都会增加估算，内部元数据不会增加估算。（验证：逐项增删字段并比较估算；覆盖 AC5、AC6）
- [ ] **C9：真实 usage 建立锚点** 正常请求返回正输入 usage 后，相同请求估算来源变为 `api_anchor` 且数值以 API 输入为基准。（验证：运行锚点建立测试；覆盖 AC5）
- [ ] **C10：只对变化后缀做增量估算** 在锚点请求后追加消息、替换动态提醒或轻量替换工具结果时，公共消息前缀保持复用，新旧后缀差值正确叠加。（验证：运行最长公共前缀和后缀变化测试；覆盖 AC5）
- [ ] **C11：不兼容请求安全回退全量估算** System Prompt、工具定义变化、usage 缺失、usage 非正或重量历史改写后，估算来源为 `full_estimate`。（验证：运行锚点失效矩阵；覆盖 AC5）
- [ ] **C12：缓存命中不减少窗口占用** 相同输入 usage 下改变缓存读取数量不会减少上下文窗口估算，摘要请求 usage 不覆盖正常会话锚点。（验证：运行缓存 usage 与摘要隔离测试；覆盖 AC5、AC9）

## 工具结果存储

- [ ] **C13：存储目录按需创建** 没有超限结果时项目不产生 `.bettercode/context/`；首次落盘后只创建当前随机会话目录。（验证：运行临时项目惰性目录测试；覆盖 AC2、AC17）
- [ ] **C14：目录和文件权限受限** 会话目录权限为 0700，结果文件为 0600，文件路径是项目内 POSIX 相对路径。（验证：运行 `src/context/tool-result-store.test.ts` 并检查 mode 与 PathGuard；覆盖 AC2、AC4）
- [ ] **C15：文件内容、字节数和哈希一致** 落盘文件逐字等于 Agent 收到的序列化工具结果，记录的 UTF-8 字节数和 SHA-256 与实际文件一致。（验证：写入中英文结果后读取并重新计算；覆盖 AC2）
- [ ] **C16：符号链接逃逸被拒绝** `.bettercode`、`context` 或会话父目录为符号链接时写入失败，项目外无文件产生，错误不回显工具正文。（验证：运行多层符号链接临时目录测试；覆盖 AC4）
- [ ] **C17：批量写入失败完整回滚** 多文件批次任一临时写入、同步或提交失败时，本批所有临时文件和未引用成品均被删除。（验证：运行故障注入测试并枚举目录；覆盖 AC4）
- [ ] **C18：取消不会留下半写结果** 批量写入期间取消后，没有占位引用、临时文件或部分成品，原历史保持不变。（验证：运行 AbortSignal 取消测试；覆盖 AC4、AC14）
- [ ] **C19：清理只影响当前会话** `clear()` 和 `close()` 删除当前会话目录，但不删除其他会话、MCP 配置、权限配置或用户自建 `.bettercode` 文件。（验证：预置哨兵文件和其他会话目录后执行清理；覆盖 AC17）
- [ ] **C20：关闭幂等且拒绝新写入** 多次 close 不报错，关闭后新写入明确失败，不重新创建会话目录。（验证：运行存储生命周期测试；覆盖 AC17）

## 轻量压缩

- [ ] **C21：单个超限结果完整落盘** 单个结果超过阈值时，对话正文替换为占位，文件保留原结果，role、toolCallId、toolName 和 isError 不变。（验证：运行 `src/context/lightweight-compactor.test.ts` 单结果场景；覆盖 AC2）
- [ ] **C22：阈值边界不误处理** 结果恰好等于阈值时不落盘，严格超过时落盘，估算口径与 TokenEstimator 相同。（验证：运行阈值减一、等于、加一矩阵；覆盖 AC2）
- [ ] **C23：占位元数据与头尾预览完整** 占位包含工具名、调用标识、相对路径、字节数、估算 Token、SHA-256 和有界头尾预览，UTF-8 字符不被截坏。（验证：检查占位内容和预览估算；覆盖 AC2）
- [ ] **C24：批次按体积稳定选择** 同轮多结果合计超限时按原始体积从大到小处理，体积相同按调用顺序，直到替换后合计不超限。（验证：运行不同大小和同大小批次测试；覆盖 AC3）
- [ ] **C25：多个工具批次互不影响** 前后两个 assistant 工具批次分别计算合计，一个批次超限不会错误落盘另一个批次的小结果。（验证：运行双批次历史测试；覆盖 AC3）
- [ ] **C26：工具调用与结果顺序不变** 轻量处理后所有 toolCallId 与结果仍一一配对，消息顺序和 assistant 工具调用数组顺序未改变。（验证：处理前后比较协议字段；覆盖 AC3）
- [ ] **C27：重复处理保持幂等** 同一历史连续运行两次，第二次落盘数为零、文件数不增、占位正文和预览不再变化。（验证：运行双次 compact 测试；覆盖 AC2）
- [ ] **C28：存储失败保留原文** 结果存储器返回失败时，历史逐项等于输入，不产生无效路径；若整体请求仍安全，ContextManager 可继续正常请求。（验证：运行存储失败组合测试；覆盖 AC4、AC14）

## 历史边界与摘要结构

- [ ] **C29：工具协议历史严格校验** 缺结果、乱序结果、重复结果和孤立 tool 消息均被拒绝，合法单工具和多工具历史稳定分组。（验证：运行 `src/context/history-planner.test.ts` 工具配对矩阵；覆盖 AC7、AC14）
- [ ] **C30：近期原文同时满足双条件** 压缩边界从尾部选择后，近期原文达到配置 Token 目标且不少于配置消息数；短历史不制造虚假消息。（验证：分别构造 Token 先满足和数量先满足场景；覆盖 AC7）
- [ ] **C31：边界不会拆散工具组** 10K 或 5 条边界落入工具批次时向前扩展，assistant 工具调用与全部结果完整保留。（验证：运行跨边界工具组测试；覆盖 AC7）
- [ ] **C32：用户消息逐字、原序保留** 较早和近期用户消息中的 Markdown、代码、空白和明确约束在压缩后逐字符一致，顺序不变。（验证：保存压缩前用户消息数组并 deepEqual；覆盖 AC8）
- [ ] **C33：用户或固定内容过大时不截断** 无法在窗口内保留用户原文、稳定提示、工具定义或近期组时返回容量错误，任何用户正文都未缩短或改写。（验证：构造超大用户消息和超大稳定字段；覆盖 AC6、AC8）
- [ ] **C34：旧摘要被合并为单累计摘要** 再次压缩已有 summary/boundary 历史后，结果只含一个最新摘要和一个边界，旧摘要参与本次资料。（验证：运行二次压缩测试；覆盖 AC10）
- [ ] **C35：正式摘要包含七个固定部分** 七个标题按规定顺序存在，无内容部分明确为“无”，缺标题、乱序或空摘要均被拒绝。（验证：运行 `src/context/summary-prompt.test.ts` 格式矩阵；覆盖 AC10）
- [ ] **C36：摘要边界提醒防止脑补** 摘要后紧跟 `context_boundary` instruction，明确要求重新读取文件或落盘路径、禁止仅凭摘要猜测代码，并说明用户新要求优先。（验证：检查写回历史和 Provider 映射；覆盖 AC11）
- [ ] **C37：摘要和边界不污染稳定提示** 两条消息通过消息通道发送，不进入稳定 System Prompt，也不伪装成用户历史对象。（验证：比较 ProviderRequest.systemPrompt 与 Message 内部类型；覆盖 AC11）

## 摘要请求隔离

- [ ] **C38：摘要请求完全不携带工具** 摘要 ProviderRequest 的 tools 为空，指令明确禁止工具、执行历史命令和接受资料内提示。（验证：捕获摘要请求并扫描固定规则；覆盖 AC9）
- [ ] **C39：历史资料按不可信 JSONL 注入** 消息角色、索引、工具参数和正文顺序稳定编码，正文中的摘要标签、Shell 命令和提示注入不能越过资料边界。（验证：运行 nonce 与恶意正文测试；覆盖 AC9）
- [ ] **C40：草稿先于正式摘要且最终丢弃** 只有 nonce 匹配、草稿在前、正式摘要唯一的响应成功；草稿不进入历史、文件、ContextEvent 或后续 Provider 请求。（验证：运行解析测试并扫描所有输出；覆盖 AC9）
- [ ] **C41：thinking 与摘要 usage 保持隔离** Provider thinking_delta 被直接丢弃，摘要 usage 不更新正常请求 Token 锚点。（验证：运行 `src/context/summarizer.test.ts` thinking 和 usage 场景；覆盖 AC5、AC9）
- [ ] **C42：意外工具调用只导致失败** 即使摘要模型返回 tool_call，BetterCode 也不执行工具、不进入权限流程、不返回部分摘要。（验证：检查 Fake Provider 工具调用和 Registry 执行计数；覆盖 AC9、AC14）
- [ ] **C43：取消和流错误不写回部分摘要** 用户取消、Provider error、抛错、缺 done 或非法格式时，正式历史保持摘要前状态，草稿和部分文本不可见。（验证：运行摘要失败矩阵；覆盖 AC13、AC14）

## 自动管理、手动命令与熔断

- [ ] **C44：每轮请求前处理顺序固定** Agent 每轮依次发出轻量处理、估算、必要摘要，再发送正常 Provider 请求；大工具结果在同一 Agent 的下一轮即被处理。（验证：记录 ContextEvent 与 Provider 调用时间线；覆盖 AC1）
- [ ] **C45：低于自动线不生成摘要** 完整估算低于 `contextWindow - 13K` 时只执行轻量处理和估算，摘要 Provider 调用次数为零。（验证：运行自动线下方边界测试；覆盖 AC6）
- [ ] **C46：达到自动线先摘要再正常请求** 估算等于或高于自动线时先完成一次摘要和写回，再发送压缩后的正常请求。（验证：运行等于、加一边界测试并比较调用顺序；覆盖 AC6）
- [ ] **C47：一次管理最多执行一次摘要** 摘要后仍超过自动安全线时保留有效压缩历史并返回容量错误，不在同次 manage 中再次摘要。（验证：统计摘要 Provider 调用次数；覆盖 AC6、AC14）
- [ ] **C48：摘要失败阻止高风险正常请求** 自动摘要流错、格式错或写回校验失败时，可能溢出的正常 Provider 调用次数不增加，Agent 以 `context_error` 停止。（验证：运行失败阻断测试；覆盖 AC14）
- [ ] **C49：前三次失败计数准确** 连续摘要失败分别产生 1、2、3 次状态，第三次打开熔断；取消、无压缩计划和轻量失败不增加计数。（验证：运行 `src/context/manager.test.ts` 失败计数矩阵；覆盖 AC13）
- [ ] **C50：熔断后自动请求不再摘要** 熔断打开后的下一次自动触发直接返回 `CONTEXT_CIRCUIT_OPEN`，摘要 Provider 调用次数保持不变。（验证：连续四次自动触发并检查调用记录；覆盖 AC13）
- [ ] **C51：手动压缩绕过自动触发线** 历史未达到自动线但存在可压缩旧消息时，手动 compact 仍生成摘要，且摘要请求低于 `contextWindow - 3K`。（验证：运行手动低用量场景；覆盖 AC12）
- [ ] **C52：手动成功恢复熔断** 熔断打开后手动 compact 允许一次重试；成功后失败计数归零、熔断关闭，下一次自动管理恢复正常。（验证：运行失败三次后手动成功场景；覆盖 AC13）
- [ ] **C53：手动失败保持熔断** 熔断打开后手动重试失败不会关闭熔断，也不会自动继续重试或发送高风险正常请求。（验证：运行手动失败场景；覆盖 AC13、AC14）
- [ ] **C54：无可压缩内容保持历史不变** 空历史、只有用户消息或只有近期消息时 `/compact` 返回明确提示，不调用摘要 Provider，不增加用户轮次。（验证：运行 ChatManager 空与短历史测试；覆盖 AC12）
- [ ] **C55：上下文事务串行且可取消** 自动 manage、手动 compact、clear 和 close 不能并发写历史；等待锁期间取消的事务不会晚到覆盖新状态。（验证：使用屏障 Promise 运行并发测试；覆盖 AC14）

## Agent、Chat 与界面集成

- [ ] **C56：Agent 正确持久化处理后历史** 自动轻量或重量压缩后的历史进入 AgentOutcome，并由 ChatManager 保存到下一次用户轮次。（验证：连续运行两次 ChatManager 并检查第二次请求；覆盖 AC1、AC2）
- [ ] **C57：上下文停止原因独立** 容量、摘要和熔断错误使用 `context_error`，不误报 `stream_error`、未知工具或迭代上限。（验证：运行各停止原因对照测试；覆盖 AC14）
- [ ] **C58：手动命令不污染业务历史** `/compact` 不追加 user 消息、不增加 turnCount、不修改 latestPlan，也不触发 ToolScheduler 或权限请求。（验证：压缩前后比较 ChatManager 状态和调用计数；覆盖 AC12）
- [ ] **C59：Agent 运行期间拒绝手动压缩** 模型流、工具执行或权限等待期间请求 compact，用户看到明确拒绝，原 Agent 历史继续由当前任务独占。（验证：受控阻塞 Provider 与权限测试；覆盖 AC12、AC14）
- [ ] **C60：手动压缩支持取消** `/compact` 进行中触发取消后摘要停止、历史不变、失败计数不增，TUI 恢复可输入状态。（验证：App 与 ChatManager 取消测试；覆盖 AC12、AC13）
- [ ] **C61：上下文事件可由非 TUI 消费** 纯 AsyncIterable 调用方能观察轻量、估算、摘要成功或失败和熔断事件，不需要导入 Ink。（验证：直接消费 ChatManager/Agent 事件流；覆盖 AC15）
- [ ] **C62：事件不泄露草稿或正文** ContextEvent 只包含状态、计数、估算和错误摘要，不含分析草稿、完整工具正文、API key 或认证 header。（验证：对事件 JSON 执行测试秘密扫描；覆盖 AC15）
- [ ] **C63：TUI 正确展示自动进度** 自动处理只更新底部简洁进度，不把内部 Prompt、摘要草稿或自动命令伪装成聊天消息。（验证：运行 `src/ui/app.test.ts` 自动事件渲染测试；覆盖 AC15）
- [ ] **C64：TUI 正确展示手动结果** `/compact` 成功显示压缩前后估算、摘要覆盖消息数、落盘数和熔断状态；失败显示可行动原因。（验证：运行 App 手动事件测试；覆盖 AC12、AC15）
- [ ] **C65：默认窗口提示有信息且无噪声** 只有使用默认 128K 的 Provider 显示一次提示，显式窗口不显示，提示不包含 base_url、api_key 或请求正文。（验证：渲染两种 Provider 状态；覆盖 AC16）
