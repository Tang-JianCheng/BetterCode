# BetterCode 团队协作系统 Checklist

> 每一项都通过运行测试、执行命令或观察可见状态验证。验收时记录实际结果，不以“代码看起来正确”代替证据。

## 配置与启动

- [ ] `teams` 配置缺省时 BetterCode 按原有方式启动，Coordinator 默认为关闭。（对应 AC20；验证：运行配置加载测试和既有启动装配测试，观察无团队配置不报错。）
- [ ] 合法的 Mailbox、Runtime、Integration 和自定义终端配置被完整解析为预期值。（对应 AC4、AC20；验证：运行配置加载测试，比较解析结果。）
- [ ] 未知字段、非法超时、心跳关系错误、重复适配器和非法占位符被启动校验拒绝。（对应 AC4、AC20；验证：逐个加载非法配置，观察明确错误。）
- [ ] 只有配置开关和 `BETTERCODE_COORDINATOR_MODE=1` 同时满足时 Coordinator 能力为 active。（对应 AC16；验证：运行四种开关组合测试。）
- [ ] 环境变量在进程启动后改变不会悄然切换当前 Coordinator 权限。（对应 AC16；验证：启动后修改测试进程环境，观察 capability 快照不变。）

## 团队生命周期

- [ ] `/team create <名称>` 创建持久团队，`/team list` 能查询到团队及状态。（对应 AC1；验证：在临时用户目录执行命令并重新加载仓库。）
- [ ] 空名称、路径分隔符、`.`、`..`、控制字符、过长名称和符号链接逃逸被拒绝。（对应 AC1、AC19；验证：运行名称和路径守卫测试。）
- [ ] 同一主会话可以保存多个团队，但任一时刻只有一个活跃团队。（对应 AC1；验证：创建并依次 use 两个团队，查询 session 绑定。）
- [ ] 切换活跃团队后，成员、任务、审批和邮箱数据不串线、不丢失。（对应 AC1；验证：两个团队写入同名成员与任务后往返切换并比较。）
- [ ] 团队 repositoryId 与当前项目不一致时不能被激活。（对应 AC1、AC19；验证：从另一临时 Git 仓库尝试 use。）
- [ ] 单个损坏团队被隔离并产生诊断，其他团队和普通 BetterCode 仍可启动。（对应 AC2、AC19；验证：损坏一份团队文件后重新扫描。）
- [ ] 原子快照写入失败时保留上一 revision 的完整有效数据。（对应 AC2、AC19；验证：注入 rename/fsync 失败并重新读取。）
- [ ] 并发 revision 冲突返回结构化冲突，不覆盖较新的团队状态。（对应 AC19；验证：两个写入者以同一 revision 更新。）

## 启动恢复

- [ ] BetterCode 重启后恢复团队、成员、任务、邮箱、审批、上下文和 Worktree 元数据。（对应 AC2；验证：构造完整状态、重建服务并逐项查询。）
- [ ] 重启前 `running` 和 `stopping` 成员恢复为 `interrupted`，不会自动重复执行。（对应 AC2；验证：持久化运行状态后递增 generation 并恢复。）
- [ ] 重启前待审批请求保持 pending，审批编号和计划版本不变。（对应 AC2、AC11；验证：恢复后查询审批记录。）
- [ ] 空闲成员的消息历史、Token、邮箱 cursor 和当前工作目录可恢复。（对应 AC2、AC12；验证：恢复上下文快照并继续一次任务。）
- [ ] 新 generation 会使旧 Worker 租约失效，旧进程不能继续写成员状态。（对应 AC2、AC19；验证：用旧 generation 写入并观察拒绝。）
- [ ] 未配对的副作用工具日志使成员保持 interrupted，Lead 未明确处理前不能恢复。（对应 AC2、AC19；验证：只写 `tool_started` 后尝试 resume。）

## 成员与角色

- [ ] 合法成员继承引用角色的提示、Provider、工具限制、权限模式和最大迭代数。（对应 AC3；验证：创建成员并检查冻结的运行快照。）
- [ ] 缺失、禁用、字段非法或引用未知工具的角色不能创建成员。（对应 AC3；验证：逐类创建并检查结构化诊断。）
- [ ] 成员创建任一步失败时，花名册不存在半初始化有效成员，残留资源有明确处理结果。（对应 AC3、AC19；验证：注入 Worktree 和后端启动失败。）
- [ ] 同一团队不能创建重名成员，成员名不能占用 Lead 保留身份。（对应 AC3；验证：重复创建和创建 `lead`。）
- [ ] 角色热更新只影响后续恢复或新运行，正在运行成员保持启动时快照。（对应 AC3；验证：运行中修改角色快照并比较工具集。）
- [ ] 成员工具能力增加副作用工具后，不能继续在共享 Lead 目录恢复。（对应 AC5；验证：只读角色变更为含 Shell 后 resume。）

## 后端选择

- [ ] 自动模式在 tmux 可用时选择 tmux，不继续探测低优先级后端。（对应 AC4；验证：Fake ProcessRunner 返回 tmux 可用并检查调用序列。）
- [ ] tmux 不可用且当前终端为 WezTerm 时选择 WezTerm。（对应 AC4；验证：模拟环境与探测结果。）
- [ ] tmux、WezTerm 不可用且当前终端为 iTerm2 时选择 iTerm2。（对应 AC4；验证：模拟 macOS iTerm2 环境。）
- [ ] 内置终端不可用时按配置顺序探测自定义终端适配器。（对应 AC4；验证：配置两个适配器并检查选择结果。）
- [ ] 只有协程可用时，自动创建失败并列出探测诊断，不会静默启动协程。（对应 AC4；验证：所有独立后端 probe 失败，检查没有 coroutine spawn。）
- [ ] 显式指定 `coroutine` 后可以创建协程成员。（对应 AC4；验证：对同一环境显式重试并观察成功。）
- [ ] 显式指定不可用的独立后端时直接失败，不降级到其他后端。（对应 AC4；验证：显式 tmux 且 probe 失败。）
- [ ] tmux、WezTerm、iTerm2 和自定义适配器启动命令只携带 Worker 描述文件路径，不包含 API Key、任务或消息正文。（对应 AC4、AC20；验证：检查 Fake ProcessRunner 收到的 argv。）
- [ ] 窗格唤醒失败不会丢失已落盘消息，低频轮询仍能发现工作。（对应 AC10、AC19；验证：让 wake 失败后触发 poll。）

## 工作目录隔离

- [ ] 只含普通只读工具的成员共享 Lead 项目根目录。（对应 AC5；验证：创建只读角色并观察成员 rootDir。）
- [ ] 含写文件、改文件、Shell 或任一普通副作用工具的成员使用专属 Worktree。（对应 AC5；验证：分别创建四类角色并检查 Worktree。）
- [ ] 窗格后端和协程后端使用相同的 Worktree 判定规则。（对应 AC5；验证：对相同角色创建两种后端并比较。）
- [ ] Worktree 初始化完成前成员不能进入 idle 或 running。（对应 AC5、AC19；验证：延迟初始化并观察状态。）
- [ ] 成员任务结束进入 idle 时仅释放租约，不自动 finalize 长期 Worktree。（对应 AC5、AC12；验证：完成任务后检查目录和元数据仍存在。）
- [ ] 成员恢复时路径、权限、Hook、项目指令、记忆和读取缓存均以成员绝对 cwd 为边界。（对应 AC5、AC20；验证：在两个 Worktree 放置不同配置并分别运行读取场景。）

## 工具作用域

- [ ] 未激活团队的主 Agent Provider 工具列表中不存在任何 `team_*` 工具。（对应 AC6；验证：捕获 ProviderRequest.tools。）
- [ ] 活跃 Team Lead 只看到 Lead 工具和当前普通工具，不看到成员专属审批提交能力。（对应 AC6；验证：检查 Lead 可见动作和执行授权。）
- [ ] 团队成员只看到成员协作动作，不能创建团队、派生成员、批准自己的计划或集成代码。（对应 AC6；验证：捕获成员工具列表并伪造禁用 action。）
- [ ] 普通定义式子 Agent 和 Fork 子 Agent 永远看不到 `team_*` 工具。（对应 AC6；验证：运行两类过滤测试。）
- [ ] 角色定义显式引用 `team_*` 工具时产生 `FORBIDDEN_TOOL`。（对应 AC6；验证：加载测试角色。）
- [ ] Provider 可见工具快照与 Scheduler 执行允许集合一致，模型伪造隐藏工具只能得到 `TOOL_UNAVAILABLE`。（对应 AC6；验证：Fake Provider 构造隐藏工具调用。）
- [ ] Skill 白名单、Plan Mode、团队身份和 Coordinator 组合时不会重新放开上层已拒绝工具。（对应 AC6、AC16；验证：运行可见性组合矩阵。）

## 共享任务

- [ ] Lead 可以创建、查询、更新、分派、取消和重新打开任务。（对应 AC7、AC8；验证：逐动作执行并观察历史。）
- [ ] 未知依赖、自依赖、重复依赖和多节点循环依赖均被拒绝。（对应 AC7；验证：运行 DAG 边界场景。）
- [ ] 合法依赖图得到稳定拓扑顺序，前置任务未完成时后续任务保持 blocked。（对应 AC7；验证：创建链式和菱形任务图。）
- [ ] 前置任务完成后后继任务按是否分派进入 pending 或 ready。（对应 AC7；验证：完成前置任务并观察状态。）
- [ ] 前置任务失败、取消或 reopened 后，尚未开始的后继任务重新 blocked 并显示原因。（对应 AC7；验证：依次改变前置终态。）
- [ ] 一个任务同一时刻只有一个主要负责人，重复分派不会产生双执行。（对应 AC8；验证：两个成员并发 assign 同一任务。）
- [ ] 成员只能读取、更新和完成分派给自己的任务。（对应 AC8；验证：成员 A 操作成员 B 的任务并观察拒绝。）
- [ ] 重新分派前原负责人执行被安全停止，历史中保留旧负责人和原因。（对应 AC8；验证：运行中 reassign。）
- [ ] 代码任务只有在分支、提交和工作目录状态可检查后才可标记为可集成。（对应 AC8、AC15；验证：缺 commit、脏 Worktree 和合法 commit 三种报告。）
- [ ] 终态不会被迟到事件覆盖，显式 reopen 会记录新状态和操作者。（对应 AC8、AC19；验证：完成后注入迟到 running，再执行 reopen。）

## 邮箱与协议

- [ ] 消息 ID、sender、timestamp 和默认未读状态由系统生成，工具参数不能伪造。（对应 AC9；验证：传入伪造字段并读取落盘消息。）
- [ ] 多协程和模拟独立进程并发写同一邮箱时消息无丢失、无覆盖且每条只出现一次。（对应 AC9；验证：并发追加后统计 ID。）
- [ ] 锁竞争按上限重试，超时返回结构化错误，不损坏原邮箱。（对应 AC9、AC19；验证：持有锁超过 lock timeout。）
- [ ] 未超时锁、超时但 PID 仍活跃的锁不会被错误回收。（对应 AC9；验证：构造两类锁并尝试获取。）
- [ ] 超时且持有者失效的锁可安全回收，旧持有者不能删除新锁。（对应 AC9；验证：模拟死 PID 与实例 ID 变化。）
- [ ] 点对点消息只能发给注册成员或 Lead，跨团队和路径式收件人被拒绝。（对应 AC10；验证：发送未知、跨团队和 `../` 收件人。）
- [ ] 广播展开为每个收件人的独立消息，单个成员标记已读不影响其他成员。（对应 AC10；验证：广播后分别读取和标记。）
- [ ] text、task、status、approval、idle、interrupted 和 system 协议都校验关联字段。（对应 AC10；验证：每类合法和缺字段消息各执行一次。）
- [ ] 广播部分投递失败时返回逐收件人结果，已成功消息不回滚。（对应 AC10、AC19；验证：让一个邮箱写入失败。）
- [ ] 唤醒发生在消息成功落盘之后，唤醒失败只产生诊断。（对应 AC10、AC19；验证：记录 store 与 wake 调用顺序。）

## 审批门禁

- [ ] 需要审批的成员领取每个任务后提交独立审批请求，planVersion 单调递增。（对应 AC11；验证：连续提交两版计划。）
- [ ] 等待审批时成员 Provider 只看到普通只读工具和成员协作工具。（对应 AC11；验证：捕获审批期工具定义。）
- [ ] 等待审批时伪造写文件、Shell 或其他副作用调用在执行前被结构化拒绝。（对应 AC11；验证：Fake Provider 强制发出副作用调用。）
- [ ] 匹配 team、task、member、approvalId 和 planVersion 的 approve 放行当前计划。（对应 AC11；验证：批准后执行一次允许副作用工具。）
- [ ] reject 不放行工具，并允许成员根据意见提交新版本。（对应 AC11；验证：驳回后尝试执行，再提交新计划。）
- [ ] 旧版本、重复响应、错误任务、错误成员、普通文本和成员自批均不生效。（对应 AC11；验证：逐种构造响应。）
- [ ] 任务改派、reopen 或新计划会使旧 pending/approved 审批 superseded。（对应 AC11；验证：查询审批历史和当前授权。）

## 成员运行与恢复

- [ ] 首次任务从角色固定指令和任务消息启动，不继承主 Agent 临时历史或 Skill。（对应 AC3、AC12；验证：捕获成员首个 ProviderRequest。）
- [ ] 每轮模型响应与工具结果完整配对后保存消息、Token、邮箱 cursor 和安全迭代号。（对应 AC12、AC19；验证：运行多轮成员并检查快照。）
- [ ] 副作用工具执行前写 started，执行后写 finished，顺序早于和晚于真实执行。（对应 AC12、AC19；验证：使用观察器记录调用顺序。）
- [ ] 成员自然停止后任务结果、成员 idle 和上下文快照均已持久化，再通知 Lead。（对应 AC12、AC13；验证：记录领域更新与 mailbox send 顺序。）
- [ ] BetterCode 重启后向空闲成员分派新任务，成员从原上下文继续而不是重新创建。（对应 AC12；验证：比较恢复前后消息前缀和成员 ID。）
- [ ] 普通广播和纯系统通知不会无条件唤醒全部空闲成员。（对应 AC12；验证：广播后检查后端 wake 次数。）
- [ ] 任务分派、审批响应和明确 direct wake 能唤醒目标空闲成员。（对应 AC12；验证：逐类消息检查 wake。）
- [ ] 上下文恢复时角色、工具、权限、后端和 cwd 任一校验失败都会保持消息未丢失并通知 Lead。（对应 AC12、AC19；验证：逐层注入失败。）

## Team Lead 编排

- [ ] Lead 可以创建依赖任务、创建成员、分派、处理审批并查询整体阻塞与 Token 用量。（对应 AC13；验证：运行完整多成员协作场景。）
- [ ] 成员可以直接互发消息并通过共享任务协作，不需要 Lead 转发普通消息。（对应 AC13；验证：成员 A 发给 B，B 从自身邮箱读取。）
- [ ] 任务通知已发送但持久化状态未完成时，Lead 不会推进依赖任务或开始集成。（对应 AC13；验证：注入仅有通知无终态场景。）
- [ ] 任务完成、成员中断、审批请求和投递失败会进入 Lead Inbox，并在下一自然请求边界注入。（对应 AC13、AC19；验证：prepare/commit 后检查 instruction 消息。）
- [ ] Team Inbox 不主动唤醒主 Agent，不打断正在进行的模型流。（对应 AC13；验证：运行主请求期间完成成员任务，检查无额外 Provider 调用。）

## 终止与取消

- [ ] 运行、待审批、空闲、已中断和失败成员都可被 Lead 终止。（对应 AC14；验证：逐状态调用 terminate。）
- [ ] 终止先发取消并等待，超时后才升级后端终止，结果标明是否可能有未完成操作。（对应 AC14；验证：正常退出和忽略取消两种后端。）
- [ ] 重复终止幂等，不影响其他成员或其他团队。（对应 AC14；验证：连续两次终止并检查旁路成员。）
- [ ] 终止后当前任务转为取消、失败或待重新指派，Lead 收到通知。（对应 AC14；验证：检查任务历史和 Lead Inbox。）
- [ ] 终止不会自动删除成员上下文、邮箱、任务历史或 Worktree。（对应 AC14；验证：终止后逐项查询文件与状态。）

## Git 集成

- [ ] Lead 工作区有未提交修改、HEAD 不可识别或成员代码状态不安全时拒绝开始集成。（对应 AC15；验证：逐类构造不安全 Git 状态。）
- [ ] 集成使用独立临时 Worktree 和分支，按任务 DAG 的稳定拓扑顺序合并。（对应 AC15；验证：检查 IntegrationRecord 和 Git 历史。）
- [ ] 无冲突场景完成全部合并和验证后，Lead 分支只发生一次 ff-only 更新。（对应 AC15；验证：比较开始与结束 HEAD、reflog 和提交图。）
- [ ] 可解决冲突场景暂停为 conflicted，解决后 continue 能完成剩余任务。（对应 AC15；验证：构造冲突、写入解决并继续。）
- [ ] 不可解决冲突执行 abort 后，Lead HEAD 与工作区保持开始前状态。（对应 AC15；验证：对比 hash 和 status。）
- [ ] 验证命令失败时不 finalize，Lead 分支不改变并保留失败输出摘要。（对应 AC15；验证：配置退出码非零命令。）
- [ ] 集成期间 Lead HEAD 被其他提交推进时 finalize 被拒绝，不覆盖新提交。（对应 AC15、AC19；验证：开始后推进 Lead 分支。）
- [ ] 成功集成的干净 Worktree 在确认提交被目标引用包含后可清理。（对应 AC15、AC18；验证：运行 removeIntegrated 并检查目录。）
- [ ] 未合入、脏目录、存在租约或检查失败的 Worktree 被保留并列出原因。（对应 AC15、AC18；验证：逐类执行清理。）

## Coordinator 模式
