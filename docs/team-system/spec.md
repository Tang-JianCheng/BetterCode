# BetterCode 团队协作系统 Spec

## 背景

BetterCode 已具备子 Agent、后台任务、角色定义、权限控制和 Git Worktree 隔离能力，但现有子 Agent 仍是围绕单个委派任务创建的短生命周期执行单元。主 Agent 无法维护一个长期存在的成员花名册，也没有共享任务、成员邮箱、计划审批、成员恢复和多分支集成机制。多个子 Agent 即使能并行运行，也只能把结果回传给主 Agent，成员之间不能直接协调，主 Agent 会成为所有信息的中转瓶颈。

本章为 BetterCode 增加长期团队协作系统。主 Agent 在激活团队后成为 Team Lead，可以拆解任务、派生成员、监督审批、收发消息并集成成员代码。团队成员复用现有子 Agent 角色与运行基础设施，但拥有长期身份、独立上下文、可恢复状态和仅在团队运行时可见的协作工具。团队状态持久化到用户目录，BetterCode 重启后仍可继续使用。

## 术语

- **团队（Team）**：按名称持久化的长期协作对象，包含负责人、成员花名册、共享任务、邮箱、审批记录和运行元数据。
- **Team Lead**：当前激活团队的负责人，负责拆解目标、创建成员、分派任务、处理审批和集成代码。
- **团队成员**：引用现有子 Agent 角色创建的长期运行身份，拥有固定名称、运行后端、工作目录、审批要求和可恢复上下文。
- **窗格后端**：在 tmux、WezTerm、iTerm2 或用户配置的终端窗格中运行完整 BetterCode 实例的独立进程后端。
- **协程后端**：在主 BetterCode 进程内复用现有 Agent Runner 的轻量运行后端。
- **共享任务**：团队内持久化的工作项，可以指定负责人、状态和直接前置依赖。
- **邮箱**：按成员名称寻址、通过文件持久化的点对点消息队列。
- **审批计划**：需要审批的成员在开始任务前提交给 Lead 的结构化执行计划。
- **Coordinator 模式**：Team Lead 只负责读取、拆解、通信、终止和 Git 集成，不直接修改项目文件的受限模式。
- **活跃团队**：当前主会话绑定并向 Lead 暴露团队管理能力的唯一团队。

## 目标

- 让 BetterCode 创建、恢复、切换和归档长期团队。
- 让 Team Lead 派生多个成员并通过共享任务表达依赖和分工。
- 让成员通过持久化邮箱直接通信，并支持点对点、广播和结构化协议消息。
- 让独立窗格与同进程协程两类运行后端共享一致的成员生命周期。
- 让需要审批的成员在每个任务开始前获得 Lead 的明确批准。
- 让空闲成员保留上下文，收到后续消息或任务时从磁盘恢复继续工作。
- 让成员并行修改发生在独立 Worktree，并由 Lead 以事务方式集成。
- 让 Coordinator 模式形成强制的只读编排边界，而不只依赖模型自律。

## 功能需求

### F1：团队生命周期与持久化

BetterCode 必须支持创建、查询、激活、切换和归档团队。团队名称必须通过严格校验，拒绝空名称、路径分隔符、`.`、`..`、控制字符和超长名称，不能借团队名称访问其他目录。

每个团队必须持久化在 BetterCode 用户目录下以团队名区分的独立目录中。持久化内容至少包括团队元数据、负责人、成员花名册、共享任务、成员邮箱、审批记录、成员上下文位置和 Worktree 信息。团队数据写入必须避免进程中断留下半份有效文件。

BetterCode 可以保存多个团队，但每个主会话同一时间只能激活一个团队。切换活跃团队不得删除、重置或混合任一团队的数据。

### F2：启动恢复与中断状态

BetterCode 重启后必须能发现并恢复合法团队及其成员、任务、邮箱、审批、上下文和 Worktree 元数据。单个团队或单份成员数据损坏时，系统必须产生可见诊断并隔离损坏对象，不能阻止其他团队和普通 BetterCode 功能启动。

进程退出前仍在运行或等待审批的成员，恢复时不得被假定仍在执行。运行中的成员必须标记为“已中断”；等待审批的请求继续保持待处理状态。Lead 可以明确选择恢复、中止或重新指派，不得在启动时自动重复执行未确认的工具操作。

### F3：成员花名册与角色复用

成员花名册必须记录唯一成员名、引用的现有子 Agent 角色、当前状态、工作目录、运行后端、后端实例标识、是否需要审批、上下文位置、当前任务、创建时间和最近活动时间。

成员必须复用启动时解析到的现有子 Agent 角色定义，继承角色提示词、模型、普通工具限制、权限模式和最大迭代数。团队层只能进一步收窄能力，并补充协作工具、运行后端、审批和持久化信息，不能放开角色或全局安全层已经拒绝的能力。

同一团队内成员名必须唯一。角色不存在、已禁用或工具配置无效时，成员创建必须失败并返回结构化诊断，不能创建半初始化成员。

### F4：成员运行后端与显式降级

成员必须支持窗格后端和协程后端。自动选择后端时优先级固定为：tmux、终端原生分屏、协程。终端原生分屏至少内置 WezTerm 和 iTerm2 适配，并允许用户为其他终端配置检测、创建和唤醒方式。

自动选择只能直接采用可用的独立窗格后端。tmux 和终端原生分屏均不可用时，创建操作必须失败、列出探测结果和可用替代项；不得静默改用协程。Lead 或用户只有显式指定协程后端重新发起创建，才能使用协程。

用户显式指定某个后端时，该后端不可用必须直接失败，不得继续降级。后端探测、选择结果和失败原因必须可观察。

### F5：成员工作目录隔离

BetterCode 必须根据成员最终可见工具的副作用能力决定工作目录。仅拥有只读工具的成员可以共享 Lead 的项目工作目录；只要成员可见任一可产生副作用的普通工具，包括可执行命令的 Shell，就必须使用专属 Git Worktree。

窗格后端和协程后端必须遵守同一隔离规则。需要 Worktree 的成员只有在 Worktree 创建和环境初始化成功后才能开始任务，所有文件、命令、权限、Hook、项目指令、记忆和读取缓存都必须以成员的绝对工作目录为边界。

团队层不得通过临时移除某个工具来把已经可写的成员降格为共享目录成员。成员工具能力发生变化并获得副作用工具时，必须先迁移到独立 Worktree 或拒绝恢复运行。

### F6：团队工具的作用域隔离

团队系统必须提供稳定的团队管理与成员协作工具，但按运行身份暴露不同工具集合：

- 未激活团队的主入口不得看到团队协作工具；
- 普通子 Agent 和 Fork 子 Agent 永远不得看到团队协作工具；
- Team Lead 只能看到创建成员、终止成员、管理共享任务、发送消息、处理审批和集成代码等 Lead 能力；
- 团队成员只能看到查询和更新自身可访问任务、发送与读取团队消息、提交审批计划和报告状态等成员能力；
- 成员不得创建团队、切换团队、派生其他成员、批准自己的计划或执行代码集成。

工具可见性必须同时约束发送给模型的工具定义和执行前校验。伪造工具调用或跨团队标识只能得到结构化拒绝，不能越权执行。

### F7：共享任务与依赖关系

共享任务必须支持创建、读取、更新、列出和取消，并记录唯一任务编号、标题、描述、负责人、状态、直接前置依赖、创建者、时间戳、结果摘要和关联分支或 Worktree。

任务依赖必须组成有向无环图。创建或修改依赖时必须拒绝未知任务、自依赖和循环依赖。任务只有在所有直接和间接前置任务完成后才能进入可领取或执行状态；前置任务失败、取消或重新打开时，依赖任务必须保持阻塞并显示原因。

任务状态变化必须遵循明确的单向规则，至少区分待处理、阻塞、待审批、可执行、执行中、已完成、失败和已取消。终态不得被迟到事件无条件覆盖；重新打开必须由 Lead 显式操作并留下记录。

### F8：成员分派与任务所有权

Team Lead 必须能把未完成任务分派给合法成员。一个任务同一时刻只能有一个主要负责人；重复分派、成员已终止、依赖未满足或成员正在执行不兼容任务时，系统必须拒绝或返回明确状态。

成员只能领取、更新和完成分派给自己的任务，不能修改依赖关系、负责人或其他成员任务。Lead 可以重新指派，但必须先安全停止原负责人对该任务的执行，并保留历史记录。

成员报告完成时必须同时写入结果摘要、上下文位置和代码状态。需要提交代码的任务只有在成员工作目录状态可检查、提交信息可定位后才能标记为可集成。

### F9：名称注册表与邮箱

每个团队必须维护成员名称注册表，把稳定成员名解析到邮箱位置、后端类型和后端实例标识。发送消息前必须通过注册表验证发件人与收件人，禁止通过路径或伪造名称访问其他团队邮箱。

每条邮箱消息至少包含唯一消息编号、发件人、收件人、正文、摘要、时间戳、是否已读和消息类型。时间戳由系统在落盘时补充，消息默认未读；发送方不能伪造时间戳、已读状态或其他成员身份。

邮箱文件必须使用锁文件保证跨协程和跨进程并发安全。获取锁失败时按有限次数和间隔重试；超过配置的陈旧时间后，只有确认锁持有者已失效或租约过期才能回收。锁竞争或写入失败必须返回结构化错误，不能损坏已有消息。

### F10：消息、广播与协议类型

团队成员和 Lead 必须支持点对点消息与广播。广播必须展开为每个目标成员的独立邮箱消息，发送方不应通过共享可变记录影响多个收件人的已读状态。

消息类型至少包括普通文本、任务通知、状态通知、审批请求、审批响应、成员空闲、成员中断和系统通知。结构化协议消息必须校验所需字段及关联对象，非法类型、未知任务、未知审批编号或不匹配的响应必须被拒绝。

窗格后端收到新消息后，系统必须额外唤醒对应窗格；协程后端通过进程内通知唤醒。唤醒失败不得丢失已落盘消息，必须记录诊断并允许稍后重试。

### F11：逐任务计划审批

标记为需要审批的成员在每个任务开始前必须发送结构化审批请求。请求至少关联审批编号、任务编号、成员名、计划正文、预计操作和计划版本。未获批准前，成员只能读取完成规划所需的信息、使用团队通信能力并等待结果，不能执行计划中的副作用操作。

Lead 必须通过结构化审批响应作出 `approve` 或 `reject` 决定，响应必须引用同一审批编号，并可附带意见。只有当前任务、当前成员和当前计划版本完全匹配的批准才有效；驳回、任务改派或计划发生实质变化后必须提交新版本重新审批。

成员不能批准自己的计划，普通文本不能被误判为批准。重复、过期和不匹配的审批响应不得改变执行权限。

### F12：成员空闲、通知与上下文恢复

成员完成任务且模型自然停止后必须进入空闲状态，持久化完整可恢复上下文，并向 Lead 发送成员空闲和任务结果通知。空闲不是成员终止，成员身份、邮箱、上下文和 Worktree 继续保留。

Lead 向空闲成员发送新的直接消息或分派新任务时，系统必须从磁盘恢复该成员上下文并继续运行，不要求重新创建成员。恢复时要重新校验角色、工具、权限、工作目录和后端可用性；校验失败时保持消息未丢失，并向 Lead 返回可操作诊断。

广播和纯系统通知默认只写入邮箱，不应无条件唤醒所有空闲成员消耗模型请求；任务分派、审批响应和 Lead 明确要求继续处理的直接消息可以唤醒成员。

### F13：Team Lead 编排流程

Team Lead 必须能把用户目标拆成带依赖的共享任务、创建或恢复成员、分派任务、跟踪状态、处理审批并在依赖满足后推进后续任务。Lead 可以查询团队整体进度、阻塞原因、成员状态、Token 用量和代码集成状态。

成员之间可以通过任务清单和邮箱直接协调，不要求所有消息经 Lead 转发。Lead 仍必须收到任务终态、审批请求、成员中断和无法投递等关键通知。

Team Lead 不得把“已发送任务”当作“已完成任务”。只有持久化任务状态和成员结果满足完成条件后，Lead 才能开始依赖任务或代码集成。

### F14：成员终止与取消

Lead 必须能终止运行中、等待审批、空闲或已中断成员。终止操作必须先发出取消信号并等待后端在有限时间内退出；超时后可以升级为后端终止，但必须记录是否可能存在未完成操作。

终止成员不得自动删除其上下文、邮箱、任务历史或 Worktree。成员当前任务必须转为失败、取消或待重新指派状态，并通知 Lead。重复终止必须幂等，不得影响同名以外的成员或其他团队。

### F15：事务式 Git 集成

Team Lead 集成代码时必须创建独立临时集成分支或等价的隔离工作目录，并按任务依赖顺序合并成员分支。不得直接在 Lead 当前分支上逐个尝试未验证的成员合并。

可自动或由 Lead 可靠解决的冲突必须在临时集成环境中完成，并在继续前运行配置的验证。任一冲突无法解决、成员分支状态不安全或验证失败时，系统必须中止并放弃本次临时集成结果，保持 Lead 当前分支和工作区不变，同时报告失败成员、冲突文件和保留的 Worktree。

只有全部成员分支合并与验证成功后，系统才能把完整集成结果一次性合入 Lead 分支。Lead 工作区存在未提交修改或其他不安全 Git 状态时，集成必须拒绝开始，不得擅自暂存、覆盖或回退用户改动。

### F16：Coordinator 双重开关

Coordinator 能力必须同时满足配置中的团队 coordinator 能力开关已启用，以及进程环境变量 `BETTERCODE_COORDINATOR_MODE=1` 已显式设置。任一条件不满足时，Coordinator 模式不得生效，并应显示未满足的条件。环境变量只在进程启动时读取，运行中修改不得悄然改变当前权限边界。

Coordinator 模式启用后，Team Lead 必须失去写文件、改文件和其他普通副作用工具，只保留只读工具、团队编排工具、成员终止、消息、审批和代码集成能力。退出或切换团队不得造成工具权限残留。

### F17：Coordinator Shell 强制限制

Coordinator 模式可以保留 Shell，但必须使用独立的强制策略，只允许 Git 状态查询、历史查询、分支与 Worktree 管理、临时集成、合并、冲突检查、合并中止和安全清理所需的白名单命令。

Coordinator Shell 必须拒绝输出重定向、可写管道、命令替换、脚本解释器、任意程序执行和普通文件修改命令。系统提示不能作为唯一防线；即使模型直接构造违规命令，也只能收到结构化拒绝。

危险命令黑名单、路径沙箱、权限规则和 Hook 仍必须在 Coordinator Shell 白名单之外继续生效，任何层级拒绝都不能被 Coordinator 模式放开。

### F18：团队归档与安全清理

归档团队后必须停止接受新任务和成员运行请求，并安全终止仍在运行的成员。归档操作必须保留团队元数据、任务、邮箱、审批和上下文，供后续审计和人工恢复。

系统只能自动删除同时满足以下条件的成员 Worktree：没有未提交修改、没有未推送提交、相关任务已完成集成、没有活动租约。任何条件不满足都必须保留目录并列出原因，不得强制删除。

归档后的团队默认不能重新激活；恢复归档团队必须是明确操作，并重新执行成员、角色、后端和 Worktree 完整性检查。

### F19：并发一致性与故障隔离

团队元数据、任务、邮箱、审批和成员状态可能被 Lead、多个协程和多个独立进程同时访问。每种持久化状态必须有明确的并发控制和版本检查，重复消息、迟到状态和进程崩溃不得无条件覆盖更新的数据。

单个成员、后端、邮箱或 Worktree 失败不得终止 Team Lead、其他成员或普通 Agent Loop。失败必须转换为结构化状态和通知，让 Lead 能重试、改派、终止或选择其他后端。

跨团队数据访问、跨成员身份伪造、越界路径和不合法状态转换必须被硬性拒绝，并留下不含密钥和完整敏感消息正文的诊断。

## 非功能需求

- **N1：安全性**：团队能力不能绕过现有危险命令黑名单、路径沙箱、权限规则、Hook、工具过滤和 Worktree 删除保护。
- **N2：持久性**：已确认写入的团队、任务、审批和邮箱消息在正常重启后必须可恢复；写入失败不得破坏上一份有效状态。
- **N3：隔离性**：成员消息、权限、Token、取消信号、读取缓存、工作目录和工具可见性不得泄漏给其他成员、普通子 Agent或其他团队。
- **N4：可观察性**：后端选择、成员状态、任务状态、审批状态、消息投递、唤醒失败、集成结果和保留 Worktree 原因必须可查询。
- **N5：确定性**：任务依赖、审批版本、状态转换、工具作用域和集成顺序必须由结构化数据决定，不依赖自然语言猜测。
- **N6：兼容性**：未创建或未激活团队时，现有主 Agent、普通子 Agent、Hook 子 Agent、Skill、权限和 Worktree 行为保持不变。
- **N7：可扩展性**：后端和终端适配器必须可扩展，但本章只保证本机进程与本机终端，不引入跨机器协议。
- **N8：资源边界**：消息锁重试、成员终止等待、后端探测和集成验证必须有超时；失败后不得无限循环或阻塞主流程。

## 不做的事

- 不支持跨机器或跨主机的分布式团队。
- 不提供成员之间的实时流式 Token 通信；协作通过持久化任务和邮箱完成。
- 不实现条件分支、资源锁、配额等更复杂的任务图约束，只支持直接依赖组成的 DAG。
- 不自动推送成员分支或集成分支到远程仓库。
- 不自动解决所有 Git 冲突；无法可靠解决时必须放弃临时集成并上报。
- 不允许普通子 Agent 或 Fork 子 Agent加入团队或使用团队工具。
- 不实现团队市场、远程成员发现或跨会话的实时在线状态服务。
- 不删除有未提交修改、未推送提交、未完成集成或活动租约的 Worktree。

## 验收标准

- **AC1（F1）**：创建两个团队并在同一主会话中切换，观察每次只有一个活跃团队，成员、任务和邮箱数据互不混合；非法团队名被拒绝。
- **AC2（F2）**：在成员运行、等待审批和空闲三种状态下模拟重启，观察团队完整恢复，运行成员变为已中断，审批和空闲上下文仍可继续处理。
- **AC3（F3）**：用合法、缺失和已禁用角色创建成员，观察合法成员继承角色限制，非法成员返回诊断且花名册无半初始化记录。
- **AC4（F4）**：分别模拟 tmux、WezTerm、iTerm2、配置适配器和仅协程可用环境，观察按优先级选择独立后端；只有协程可用时必须显式重试才能创建。
- **AC5（F5）**：创建纯只读成员和含任一副作用工具的成员，观察前者共享 Lead 工作目录、后者使用独立 Worktree，且两种后端行为一致。
- **AC6（F6）**：分别从普通主入口、普通子 Agent、Team Lead 和团队成员构造工具请求，观察只有对应身份看到并能执行允许的团队工具，伪造调用被拒绝。
- **AC7（F7）**：创建合法依赖链，并尝试未知依赖、自依赖和循环依赖，观察非法修改被拒绝；前置任务未完成时后续任务保持阻塞。
- **AC8（F8）**：分派、重新分派并完成任务，观察单一负责人约束、成员权限边界、历史记录和代码状态检查生效。
- **AC9（F9）**：多个协程和独立进程并发写同一邮箱，观察消息不丢失、不重复覆盖、身份和时间戳由系统生成，陈旧锁可安全恢复。
- **AC10（F10）**：发送点对点、广播和各类协议消息，观察字段校验、独立已读状态和后端唤醒生效；唤醒失败后消息仍保留。
- **AC11（F11）**：需要审批的成员提交计划后尝试副作用操作，观察批准前被拦截；匹配版本的批准放行，驳回、旧版本和伪造批准均不放行。
- **AC12（F12）**：成员完成后进入空闲并重启 BetterCode，再发送新任务，观察成员从原上下文恢复；普通广播不会无条件唤醒所有空闲成员。
- **AC13（F13）**：Lead 拆解含依赖任务并派给多个成员，观察成员可以直接通信，Lead 依据持久化终态推进而不是依据已发送通知推进。
- **AC14（F14）**：分别终止运行、待审批、空闲和已中断成员，观察操作幂等、任务状态正确、数据和 Worktree 保留且其他成员不受影响。
- **AC15（F15）**：对无冲突、可解决冲突、不可解决冲突和验证失败四种组合执行集成，观察只有全部成功时 Lead 分支改变，失败时 Lead 工作区保持原样并得到完整报告。
- **AC16（F16）**：分别组合配置开关和 `BETTERCODE_COORDINATOR_MODE=1`，观察只有两者同时满足时 Coordinator 生效，且工具集合按团队切换正确恢复。
- **AC17（F17）**：在 Coordinator Shell 中执行允许的 Git 集成命令以及重定向、脚本和文件修改命令，观察前者可用、后者在执行前被结构化拒绝。
- **AC18（F18）**：归档包含安全与不安全 Worktree 的团队，观察团队停止运行，安全目录被清理，不安全目录按原因保留，持久化协作记录仍可查询。
- **AC19（F19）**：注入成员崩溃、邮箱写失败、后端唤醒失败和迟到状态事件，观察故障被隔离、状态不回退、Lead 可继续管理其他成员。
- **AC20（N1-N8）**：运行现有完整检查与团队端到端场景，观察无既有功能回归、所有等待均有超时、诊断不泄露密钥或完整敏感消息正文。
