# BetterCode MCP 客户端 Spec

## 背景

BetterCode 已具备统一工具接口、工具注册中心、Agent Loop、Plan Mode 和五层权限系统，但当前工具全部由 BetterCode 内置。用户无法通过标准协议接入数据库、浏览器、代码托管平台等外部工具服务，每增加一种能力都需要直接修改 BetterCode 源码。

本章为 BetterCode 增加 MCP 客户端。用户在用户级或项目级 YAML 配置中声明 MCP Server 后，BetterCode 在启动阶段连接这些 Server，完成 MCP 初始化、工具发现和本地注册。Agent 继续通过现有工具中心调用工具，不需要感知工具来自内置实现还是 MCP Server。

## 目标

- 支持通过本地 stdio 子进程和远程 Streamable HTTP 连接 MCP Server。
- 按 MCP 标准完成初始化握手、工具列表发现和工具调用。
- 将远端工具转换为 BetterCode 现有工具能力，并接入参数校验、超时、取消、权限和 Agent Loop。
- 支持多个 Server 并行发现、连接复用和统一关闭，单个 Server 故障不影响其他 Server及内置工具。
- 从用户级和项目级配置加载 Server 列表，按 Server 名称确定性覆盖。
- 对配置、连接、协议和调用错误提供清晰但不泄露敏感值的诊断。

## 配置约定

MCP Server 使用两层独立 YAML 配置：

- 用户级：`~/.bettercode/mcp.yaml`
- 项目级：`<project>/.bettercode/mcp.yaml`

每个文件使用 `servers` map，以 Server 名称作为 key：

```yaml
servers:
  local-tools:
    transport: stdio
    command: node
    args:
      - ./scripts/mcp-server.js
    env:
      SERVICE_TOKEN: ${SERVICE_TOKEN}

  issue-tracker:
    transport: http
    url: https://mcp.example.com/mcp
    headers:
      Authorization: Bearer ${MCP_TOKEN}
```

项目级与用户级出现同名 Server 时，项目级完整定义覆盖用户级定义，不做字段级深度合并。项目级同名定义无效时，不回退到被覆盖的用户级定义，避免意外连接到用户原本配置的其他服务。

stdio 配置必须包含非空 `command`，可选 `args` 和 `env`；HTTP 配置必须包含合法 `url`，可选 `headers`。`env` 和 `headers` 的字符串值支持 `${VAR}` 环境变量展开。引用的环境变量不存在时，该 Server 配置无效并产生诊断，不把未展开占位符发送给子进程或远端服务。

## 功能需求

### F1：两层配置加载与合并

BetterCode 启动时分别读取用户级和项目级 MCP 配置。配置文件不存在时视为空配置；单层文件损坏时报告该层诊断，并继续使用另一层中仍有效的配置。

两层配置按 Server 名称合并，项目级优先。每个 Server 独立校验传输类型和所需字段；一个 Server 的配置错误不得让其他有效 Server 失效，也不得阻止 BetterCode 使用内置工具启动。

### F2：敏感配置的环境变量展开

stdio 的 `env` 值和 HTTP 的 `headers` 值支持一个字符串中出现一个或多个 `${VAR}` 占位符。展开只读取 BetterCode 启动进程的环境变量，不执行 Shell 插值或命令替换。

缺失变量时只报告变量名、配置层和 Server 名称，不输出同一字段中的其他明文内容。配置诊断、错误结果和日志不得回显完整请求头、环境变量值或认证信息。

### F3：stdio 传输

stdio 类型的 Server 由 BetterCode 启动为本地子进程。协议消息通过子进程标准输入和标准输出传输，标准错误仅作为受限诊断来源，不得混入协议消息。

启动失败、进程提前退出、协议输出损坏或调用期间断开时，仅将对应 Server 标记为不可用。关闭 BetterCode 时应结束其启动的 stdio 子进程，避免遗留后台进程。

### F4：Streamable HTTP 传输

HTTP 类型的 Server 通过配置的 URL 使用 MCP Streamable HTTP 传输。每次连接使用展开后的静态请求头，并遵循协议规定的会话标识和消息收发方式。

URL 无效、连接超时、HTTP 状态异常、响应无法解析或会话中断时，仅影响对应 Server。当前章节只支持配置静态请求头，不实现 OAuth、浏览器登录或其他交互式认证流程。

### F5：MCP 会话协议

每个 Server 会话必须依次完成以下阶段：

1. 发送初始化请求，声明 BetterCode 客户端身份和支持的能力，并验证 Server 返回的协议结果。
2. 完成初始化通知后请求工具列表，处理协议允许的分页，得到完整工具集合。
3. Agent 调用已注册工具时，向原 Server 发送工具调用请求并返回对应结果。

协议请求使用 JSON-RPC 2.0 标识进行异步配对。多个并发请求的响应即使乱序到达，也必须回到各自原始调用；未知、重复或迟到响应不得完成错误的工具调用。

### F6：远端工具适配与注册

发现到的每个 MCP 工具都包装为 BetterCode 现有工具能力，保留远端描述和输入 Schema。适配后的工具进入同一个注册中心，因此 Provider 工具定义、Agent 调度和对话历史不需要区分其来源。

本地工具名称必须稳定、唯一、符合现有 Provider 的工具命名约束，并能识别来源 Server 和远端工具。Server 名称、远端工具名称或规范化结果发生冲突时，不得覆盖已注册工具；冲突项产生诊断，其余工具继续注册。

远端 Schema 不合法或无法被现有参数校验器接受时，只跳过该工具并报告来源，不让整个 Server 或 BetterCode 启动失败。

### F7：工具调用与结果转换

Agent 调用 MCP 工具时，适配层把本地调用参数原样映射到对应 Server 和远端工具，并把取消信号传递到协议调用。调用继续受 BetterCode 工具执行超时和输出大小限制约束。

远端文本和结构化结果应转换为模型可理解的工具结果；远端声明的工具错误、JSON-RPC 错误、连接断开和结果格式错误应转换为结构化失败。当前 Provider 无法直接消费的图片、音频或二进制内容不得无界注入对话历史，应返回可识别的内容说明或受限结构化表示。

每个本地工具调用必须产生且只产生一个最终结果，并保持原工具调用标识，确保 Agent 对话历史中的工具调用与结果配对完整。

### F8：连接缓存与生命周期

每个有效 Server 在一次 BetterCode 进程生命周期内最多维护一个活动客户端会话。工具发现和后续调用复用该会话，不为每次工具调用重复启动子进程或重新握手。

多个 Server 的初始化相互独立并可并行进行。每个 Server 的连接和发现过程都有有界等待时间，避免单个无响应 Server 永久阻塞启动。

BetterCode 退出时统一关闭所有已创建客户端和传输。关闭单个客户端失败不得阻止其他客户端关闭或终端退出。

### F9：故障隔离与不可用状态

单个 Server 在配置、启动、握手、工具发现或调用阶段失败时，其他 Server 和六个内置工具继续可用。若所有 MCP Server 都失败或配置为空，BetterCode 仍可正常启动，只是不注册 MCP 工具。

Server 在启动后断开时，本章不自动重连。该 Server 已注册工具的后续调用返回稳定的不可用错误，让 Agent 可以调整方案；不得因此让 Agent Loop 或 BetterCode 主进程崩溃。

启动诊断至少能区分配置错误、环境变量缺失、传输失败、初始化失败、工具发现失败和工具注册冲突，并标明 Server 名称。诊断不得包含认证头、环境变量值或不受限的远端响应正文。

### F10：权限系统与 Plan Mode 接入

所有 MCP 工具必须经过 BetterCode 现有权限系统，不能绕过工具注册中心直接调用。远端工具明确声明只读提示时可按只读工具处理；未声明或声明为非只读时采用副作用工具的保守默认值。

权限规则使用适配后的本地工具名称，并以完整参数对象的稳定表示作为匹配目标。默认权限模式下，未命中规则的 MCP 调用需要用户确认；严格和放行模式继续遵循既有定义。

Plan Mode 只暴露远端明确声明为只读的工具。MCP Server 提供的只读提示属于 Server 自声明信息，不构成操作系统级安全保证；缺失提示的工具不得进入 Plan Mode。

BetterCode 的项目路径沙箱和危险命令黑名单只能强制约束内置专用文件工具和命令工具，无法检查远端 MCP Server 内部如何访问文件、执行命令或发起网络请求。界面和文档不得把 MCP 工具描述为受到同等文件系统隔离。

## 非功能需求

- **N1：协议兼容性**  
  遵循 MCP 标准客户端行为，不依赖特定 Server 的私有消息格式。协议版本或能力不兼容时明确拒绝对应 Server，不猜测执行。

- **N2：故障隔离**  
  配置、连接和调用故障以 Server 或工具为边界，不传播为 BetterCode 全局启动失败；内部异常必须转换为诊断或结构化工具结果。

- **N3：安全默认值**  
  缺失环境变量、非法配置、无效 Schema 和未知工具安全提示均采用失败关闭。MCP 工具缺失只读声明时按副作用处理。

- **N4：敏感信息保护**  
  认证请求头、子进程环境变量和展开后的秘密不得进入工具描述、模型上下文、普通日志或用户可复制的完整错误正文。

- **N5：响应性**  
  多 Server 初始化不因串行等待产生不必要延迟；单个 Server 的连接、发现和调用都有超时边界；工具调用取消能及时结束本地等待。

- **N6：确定性**  
  相同两层配置、环境和远端工具列表必须产生相同的合并结果、本地工具名称、权限目标和注册顺序，不依赖网络响应先后顺序。

- **N7：兼容现有能力**  
  MCP 接入不得破坏内置六工具、Agent Loop、批量工具调度、Plan Mode、权限模式、OpenAI 兼容 Provider 和 Anthropic Provider。

- **N8：可测试性**  
  配置合并、环境变量展开、两类传输、协议握手、乱序响应、工具适配、故障隔离、权限接入和生命周期关闭都能在不调用真实模型 API 的情况下验证。

- **N9：平台范围**  
  stdio 传输支持 BetterCode 当前目标平台 macOS 和 Linux。Windows 子进程命令与信号语义不在本章保证范围内。

- **N10：安全边界透明**  
  MCP Server 以独立外部服务或 BetterCode 子进程权限运行。本章不提供容器、操作系统沙箱、网络隔离或对远端服务行为的可信验证。

## 不做的事

- 不实现 MCP Resources 的发现、读取、订阅或资源模板能力。
- 不实现 MCP Prompts 的发现和获取。
- 不实现 MCP Sampling、Elicitation 或 Server 发起的模型调用。
- 不实现 Server 健康检查、心跳、自动重连、退避重试或故障自动恢复。
- 不监听工具列表变化通知，不在运行时自动新增、删除或刷新远端工具。
- 不实现 OAuth、动态客户端注册、浏览器认证或凭据刷新，只支持配置中的静态 HTTP headers。
- 不提供 MCP Server 的安装、下载、进程守护、版本升级或配置管理界面。
- 不实现网络域名、IP、端口、重定向或请求内容的权限控制。
- 不为 MCP Server 提供容器、文件系统、命令或系统调用级沙箱。
- 不修改远端工具输入 Schema，不推断缺失参数，也不对 Server 返回的业务内容做正确性背书。
- 不把 MCP 工具结果中的图片、音频或二进制内容升级为 Provider 原生多模态输入。

## 验收标准

- **AC1：两层配置合并**  
  用户级和项目级分别配置不同 Server 时两者均被发现；同名 Server 使用项目级完整定义；单层文件缺失或损坏时，另一层有效 Server 仍可加载。（覆盖 F1）

- **AC2：环境变量安全展开**  
  stdio env 和 HTTP headers 中一个或多个 `${VAR}` 能正确展开；变量缺失时只禁用对应 Server，诊断包含变量名但不泄露同字段秘密或其他认证值。（覆盖 F2）

- **AC3：stdio 完整流程**  
  使用测试 MCP 子进程启动 BetterCode 时，能够完成初始化、工具发现和工具调用；协议消息不受标准错误输出干扰，退出后子进程不残留。（覆盖 F3、F5、F8）

- **AC4：Streamable HTTP 完整流程**  
  使用本地测试 HTTP Server 时，能够携带展开后的请求头完成初始化、工具发现和调用，并正确处理会话标识；认证值不出现在诊断和模型上下文中。（覆盖 F4、F5）

- **AC5：异步请求正确配对**  
  同一 Server 上并发发起多个协议请求并让响应乱序返回时，每个调用仍取得自己的响应；未知、重复和迟到响应不会完成其他调用。（覆盖 F5）

- **AC6：工具无感注册**  
  至少两个 Server 暴露同名远端工具时，BetterCode 生成稳定且互不冲突的本地名称，Provider 能看到其描述和 Schema，Agent 能通过现有调度链调用正确 Server。（覆盖 F6）

- **AC7：无效工具隔离**  
  一个 Server 同时返回有效工具、非法 Schema 工具和命名冲突工具时，有效工具仍成功注册，无效项产生带 Server 和远端工具名的诊断且不覆盖已有工具。（覆盖 F6、F9）

- **AC8：结果与错误转换**  
  文本结果、结构化结果、远端工具错误、JSON-RPC 错误、连接断开、调用超时和取消分别得到唯一且配对完整的工具结果；二进制内容不会无界进入对话历史。（覆盖 F7）

- **AC9：连接复用与关闭**  
  连续调用同一 Server 的多个工具时只发生一次启动和初始化；多个 Server 可独立工作；BetterCode 退出后所有客户端关闭，stdio 子进程被回收。（覆盖 F8）

- **AC10：Server 故障隔离**  
  同时配置正常、拒绝连接、握手失败和工具发现失败的 Server 时，正常 Server 与内置工具继续可用；全部 MCP Server 失败时 BetterCode 仍能启动。（覆盖 F9）

- **AC11：断开后不自动重连**  
  已连接 Server 在运行中退出后，其工具调用返回稳定不可用错误，未产生新的子进程或 HTTP 会话，其他 Server 和 Agent Loop 继续运行。（覆盖 F9）

- **AC12：权限与 Plan Mode**  
  MCP 工具调用先经过现有权限判定；只读提示为真的工具可进入 Plan Mode，缺失或非只读工具不能进入；权限规则可按稳定本地名称和参数目标匹配。（覆盖 F10）

- **AC13：外部安全边界不被误报**  
  验证 MCP 工具不会被宣称为受 BetterCode 文件沙箱或危险命令黑名单强制保护，且缺失只读提示时采用副作用默认值。（覆盖 F10、N3、N10）

- **AC14：敏感信息不泄露**  
  在配置、连接、握手和调用失败场景中扫描诊断、工具结果、Provider 请求和测试日志，展开后的 env 与 headers 值均未出现。（覆盖 N4）

- **AC15：现有功能回归**  
  未配置 MCP 时，BetterCode 的启动行为、六个内置工具、Agent Loop、批量调度、权限确认、Plan Mode 及两类 Provider 测试保持通过。（覆盖 N7）

- **AC16：自动化验证**  
  配置、协议和生命周期测试使用本地伪 Server 或受控传输完成，不访问真实模型 API、不依赖公网 MCP Server，也不执行真实高危操作。（覆盖 N8）

## 增量规格：项目根 `.mcp.json` 配置桥接

### 背景

BetterCode 已具备 MCP 会话、工具适配、注册和 Agent 调用链路，但启动时只读取 BetterCode 原生 YAML。项目已经按通用客户端格式配置 `.mcp.json` 时，该文件不会进入配置加载器，导致配置看似正确却没有任何远端工具注册。

### F11：兼容配置发现与转换

BetterCode 启动时额外读取项目根 `.mcp.json` 的 `mcpServers` map，并将每个 Server 转换为现有 MCP 配置模型。stdio 支持 `command`、`args`、`env`，未声明传输类型时可由 `command` 推断；Streamable HTTP 支持 `url`、`headers`，接受 `type` 或 `transport` 声明，并可由 `url` 推断。

兼容配置复用现有环境变量展开、秘密脱敏、会话管理、工具注册、权限判定和 Agent 调度，不建立平行的工具执行通道。

### F12：三层覆盖与故障隔离

Server 按“用户级 `~/.bettercode/mcp.yaml` < 项目根 `.mcp.json` < 项目级 `.bettercode/mcp.yaml`”的优先级完整覆盖，同名项不做字段深合并。兼容文件损坏或单个 Server 无效时产生项目级诊断，其他来源和其他有效 Server 继续加载。

项目根 `.mcp.json` 必须经过项目路径保护；符号链接解析到项目外时拒绝读取，外部文件正文不得进入诊断。

### 增量非功能需求

- **N11：向后兼容。** 未配置 `.mcp.json` 时，原有两层 YAML 行为和启动结果保持不变。
- **N12：敏感信息保护。** 兼容配置中的 env、headers 和环境变量展开值沿用现有脱敏规则，测试和诊断不得输出真实项目密钥。
- **N13：确定性。** 三个来源的覆盖顺序固定，最终 Server 列表继续按名称稳定排序。

### 增量不做的事

- 不支持通用客户端私有的 OAuth、SSE 旧传输或扩展字段。
- 不修改 MCP 工具本地命名、权限语义和 Agent 调用协议。
- 不自动迁移、重写或删除用户已有 `.mcp.json`。

### 增量验收标准

- **AC17：兼容格式可用。** 项目根 `.mcp.json` 中的 stdio 和 Streamable HTTP Server 能被加载，环境变量正确展开，并转换为现有配置模型。（覆盖 F11）
- **AC18：工具调用闭环。** 从 `.mcp.json` 发现的真实本地 HTTP MCP 工具能注册到统一 ToolRegistry，并通过现有适配器完成调用和关闭。（覆盖 F11）
- **AC19：覆盖顺序稳定。** 三个来源存在同名 Server 时，项目原生 YAML 胜出；不存在同名项时三个来源完整合并。（覆盖 F12、N13）
- **AC20：错误与路径隔离。** 非法 JSON、无效 Server、缺失环境变量和符号链接逃逸只产生脱敏诊断，不影响其他有效配置或内置工具。（覆盖 F12、N12）

## 增量：/mcp 动态命令面板

### 变更内容

- F13：`McpManager` 新增 `listServerTools()`，返回每个配置 Server 的工具清单（名称、传输、是否连接、工具列表），供 `/mcp` 展示；连接失败的 Server 也包含在内并标记 `connected:false`。
- F14：`BetterCodeApplication` 暴露 `mcpServerTools`，经 `index.tsx` 注入 `App`。
- F15：新增 `/mcp` 命令（`type: ui`）与 `McpDialog` 动态面板：第一级列出全部 Server（名称左对齐、`传输 · N 工具 · 已连接/失败` 右对齐），Enter 进入选中 Server 的工具列表，第二级列出该 Server 的全部工具与描述；Esc 返回上一级，再按 Esc 退出。

### 验收补充

- AC21：`/mcp` 打开服务器面板，Enter 进入工具列表、Esc 逐级返回，方向键选择并整行高亮，超一页显示剩余数量。
- AC22：连接失败的 Server 显示「失败」状态，无工具时 Enter 不进入工具页。
- AC23：未配置任何 MCP Server 时 `/mcp` 给出提示而非空面板。
