## 基线总结

| 场景 | 改造前表现 | 主要缺口 |
|---|---|---|
| 专用工具 | 正确使用 `find_files` | 缺少 system 与工具描述的稳定双重约束 |
| 编辑前读取 | 正确执行先读、编辑、复查 | 行为主要依赖模型自行判断 |
| Plan Mode | 权限只读，但读取范围过大 | 模式规则混在用户任务中，输入成本高 |
| 环境识别 | 使用 `run_command` 后回答正确 | 没有动态环境消息，需要额外工具轮次 |

## 缓存验证

### 验证步骤

1. 使用同一个 `deepseek-v4-pro` Provider、同一个 ChatManager、Act Mode 和完整六工具定义。
2. 首次发送“不调用工具，只回复 `CACHE_ONE`”。
3. 保留同一会话历史，再发送“不调用工具，只回复 `CACHE_TWO`”。
4. 记录每次 Agent `usage` 事件的五个字段。
5. 自动化测试另外断言同一模式连续请求的 systemPrompt 和 tools 深度相等，动态 reminder 只存在于 messages。

### 实际数据

| 请求 | 输入 | 输出 | 总计 | 缓存创建 | 缓存命中 | 回复 |
|---|---:|---:|---:|---:|---:|---|
| 1 | 1427 | 26 | 1453 | 0 | 1152 | `CACHE_ONE` |
| 2 | 1446 | 25 | 1471 | 0 | 1152 | `CACHE_TWO` |

DeepSeek 自动缓存没有返回缓存创建 Token，因此统一字段为 0；两次请求均返回 `cacheReadInputTokens = 1152`，证明服务端识别并复用了稳定前缀。编辑场景和 Plan Mode 的后续轮次也分别累计命中 3712 和 18688 Token。

### 可重复性与边界

- 验证请求不修改项目文件，也不依赖临时评估内容。
- 相同 Provider、模型、模式和工具集合可重复执行上述两条消息。
- Plan 与 Act 使用不同工具集合，因此会形成各自的稳定缓存前缀，不要求跨模式共享缓存。
- Anthropic 显式缓存请求由自动化协议测试验证；本次真实运行只使用当前可用的 DeepSeek API key，没有伪造 Anthropic 命中数据。

## 最终结论

结构化 system 与动态 reminder 的边界按预期生效：稳定内容没有被环境与模式消息改写，DeepSeek 返回了可重复的真实缓存命中数据；环境注入减少了一次通用命令和一个 Agent 轮次；临时 instruction 不再进入持久历史。

专用工具选择、编辑前先读和 Plan Mode 只读边界在改造前已经表现正确，本次改造保持了这些行为。Plan Mode 的探索范围仍偏大，系统提示没有显著降低该场景的输入总量，这是后续可单独优化的剩余问题，不属于本阶段缓存与提示分层的阻塞项。
